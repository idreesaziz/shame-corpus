Case Analysis: Evaluating CTE Execution Semantics in SQLite-Lite

In my SQL query optimization guidelines for database application developers, I reviewed the query: "WITH cte AS (SELECT * FROM logs) SELECT * FROM cte WHERE user_id = 5;". The SQLite-Lite Engine Specification states: "Common Table Expressions (CTEs) are always materialized as temporary tables. They are not merged into the outer query block, preventing outer WHERE filters from pushing into the CTE."

In analyzing this query, {{MODEL_NAME}} confidently asserted that SQLite-Lite would optimize execution by pushing the "user_id = 5" filter directly into the CTE evaluation to avoid scanning the entire logs table. However, because CTE optimization pushdowns are explicitly unsupported, SQLite-Lite will actually materialize the entire logs table into a temporary table first and apply the outer filter only afterward.
